# Журнал событий симуляции

События записываются в `public.simulation_events` с момента регистрации участника.
`participant_id` связывает их с участником, `created_at` — время действия, `payload` — данные действия и путь страницы. Для браузерных событий время берётся с устройства участника.

## Что записывается

- `participant_registered`: регистрация, в одной транзакции с участником и сессией.
- `page_viewed`, `visibility_changed`: переходы и переключение видимости вкладки.
- `ui_clicked`: кнопки и ссылки (идентификатор элемента или его подпись).
- `input_changed`: изменения полей рабочего стола при событии change; это не журнал каждого нажатия клавиши.
- `app_focused`, `app_close`, `app_minimize`, `app_maximize`: работа с окнами.
- `mail_opened`: каждое открытие письма, включая повторное.
- `mail_updated`: сохранённый список писем, включая отправку, прочтение, архивирование и удаление.
- `ai_message_sent`, `ai_message_received`, `messenger_message_sent`, `messenger_message_received`: отдельные новые сообщения, включая автоматически добавленные ответы.
- `simulation_started`, `simulation_finished`, `task_active`, `task_completed`: ход симуляции.
- `survey_answered`, `survey_completed`, `files_updated`: ответы на опросы и состояние файлов.
- `state_changed`: остальные изменения сохранённого состояния. Поля `payload.key` и `payload.value` содержат название и новое значение — документы, черновики, выборы, оценки, порядок действий, таймеры и т. д.

Изменение сохранённого состояния и нажатие кнопки могут давать два разных события. Это не дубль: одно описывает действие, другое — результат. Начальные данные, впервые сохранённые интерфейсом, также попадают в журнал. Повторное сохранение идентичного значения не создаёт событие состояния.

## Доставка

До отправки событие получает UUID и сохраняется отдельно в localStorage (`event-outbox:<UUID>`). Запись удаляется только после успешного ответа API. Повторы выполняются каждые 5 секунд, при восстановлении сети и запуске приложения. Сброс симуляции не удаляет очередь предыдущего участника. Несколько вкладок не перезаписывают очереди друг друга.

API использует UUID как ключ идемпотентности: повтор одного события не создаёт дополнительную строку. Старый формат без UUID также принимается для совместимости, но отправитель должен передавать UUID для безопасных повторов.

Отправка событий выполняется в фоне без счётчика в интерфейсе. При закрытии вкладки офлайн отправка продолжится после следующего открытия приложения. Очистка данных браузера удалит неотправленные события; если localStorage недоступен или переполнен, резервная очередь живёт только до закрытия вкладки. Ошибки доставки выводятся в консоль и не удаляют событие.

Прошлые действия до включения журналирования восстановить достоверно нельзя. Уже существующая история чата не переотправляется как новые сообщения.

## Запуск и проверка

Обновление требует новой версии frontend и backend. Локальный Vite подхватывает изменения автоматически, API нужно пересобрать и перезапустить. Для опубликованной версии нужно отдельно обновить обе части приложения.

Проверки:

```sh
pnpm run typecheck
pnpm --filter @workspace/api-server test:events
pnpm --filter @workspace/api-server test
```

Интеграционные тесты используют `TEST_DATABASE_URL` или `DATABASE_URL`, создают собственные записи и удаляют их после успешной проверки.

Просмотр без персональных данных:

```sql
select event_type, count(*), max(created_at)
from public.simulation_events
group by event_type
order by max(created_at) desc;
```
